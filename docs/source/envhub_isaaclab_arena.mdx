# NVIDIA IsaacLab Arena & LeRobot

[IsaacLab Arena](https://github.com/isaac-sim/IsaacLab-Arena) provides GPU-accelerated robotics simulation for policy evaluation. LeRobot connects to Arena through the standard [EnvHub](./envhub) native vector interface and environment server.

<img

This integration supports **GR1 PINK opening the microwave**, with native GPU batching, a 512×512 robot POV camera, and standard LeRobot policy loaders and processors. Arena supports a broader environment catalog; other tasks and controllers need their own observation/action schema before they can use this provider.

## Installation

### Prerequisites

- A Linux machine with an NVIDIA GPU and driver compatible with the selected Isaac Sim runtime.
- Matching upgraded Arena, Arena EnvHub and LeRobot source checkouts. The validated stack uses Isaac Sim 6.2 and Arena's pinned Isaac Lab submodule.
- Separate simulator and policy Python environments. The native simulator uses Torch 2.11.0+cu130, NumPy 2.3.1 and Gymnasium 1.3.0; the tested policy client uses Torch 2.15.0 and Transformers 5.22.1.

<Tip warning={true}>
  The old Isaac Sim 5.1 / Isaac Lab 2.3 installation and the provider exporting
  only `make_env` are not compatible with this migration. Use the matching
  upgraded checkouts and record their exact revisions. The provider README lists
  the tested code revisions and dependency exceptions.
</Tip>

### Setup

**1. Prepare the simulator environment.** Build and start a fresh container using the matching Arena checkout's documented Docker workflow. Mount the upgraded EnvHub and LeRobot checkouts, then install the standard server inside the existing simulator environment:

```bash
export ARENA_ENVHUB=/absolute/container/path/to/isaaclab-arena-envs
export LEROBOT_SOURCE=/absolute/container/path/to/lerobot

isaaclab.sh -p -m pip install --no-deps -e "$LEROBOT_SOURCE"
isaaclab.sh -p -m pip install -r "$ARENA_ENVHUB/requirements.txt"
```

Keep the simulator's native Torch/NumPy stack. This minimal server installation preserves existing simulator packages but has documented dependency metadata conflicts; it is not a fully resolved combined policy/simulator installation. The generic EnvHub `--docker=true` image does not provision these Arena source changes and submodules.

**2. Prepare the policy environment.** From the matching LeRobot checkout on the client host:

```bash
uv sync --locked --extra smolvla --extra dataset --extra evaluation --extra remote
source .venv/bin/activate
export ARENA_ENVHUB=/absolute/client/path/to/isaaclab-arena-envs
```

The paths may differ inside and outside a container. The client still needs `env.hub_path` even when a server runs the simulator.

**3. Start the environment server.** In the simulator container, using its own `ARENA_ENVHUB` path:

```bash
export OMNI_KIT_ACCEPT_EULA=YES ACCEPT_EULA=Y
isaaclab.sh -p -m lerobot.scripts.lerobot_env_server \
    --envhub="$ARENA_ENVHUB" \
    --sim.task=gr1_open_microwave \
    --sim.kwargs='{make_env_kwargs: {device: "cuda:0", headless: true}}' \
    --max_sessions=1 --max_envs=2
```

Make port 7448 reachable from the policy client. The examples below use the same host's loopback address. Wait for the server's `Serving` message before evaluating; the first launch may compile shaders and load assets. One application owns one native batch and can rebuild it when the requested batch size changes. Stop the server normally after clients disconnect.

## Evaluating Policies

### Pre-trained Policies

| Policy                                                                                   | Architecture | Task          | Checkpoint revision                        |
| :--------------------------------------------------------------------------------------- | :----------- | :------------ | :----------------------------------------- |
| [smolvla-arena-gr1-microwave](https://huggingface.co/nvidia/smolvla-arena-gr1-microwave) | SmolVLA      | GR1 microwave | `1fab07da0ffb6c263c9703c296745a730a6ea696` |
| [pi05-arena-gr1-microwave](https://huggingface.co/nvidia/pi05-arena-gr1-microwave)       | PI0.5        | GR1 microwave | `9cf88e758aeb86be15e0f44364cad19cede23188` |

### Evaluate SmolVLA

Run from the policy environment:

```bash
lerobot-eval \
    --policy.path=nvidia/smolvla-arena-gr1-microwave \
    --policy.pretrained_revision=1fab07da0ffb6c263c9703c296745a730a6ea696 \
    --policy.device=cuda \
    --env.type=envhub \
    --env.hub_path="$ARENA_ENVHUB" \
    --env.task=gr1_open_microwave \
    --env.server.endpoint=tcp/127.0.0.1:7448 \
    --rename_map='{"observation.images.robot_pov_cam_rgb":"observation.images.robot_pov_cam"}' \
    --eval.batch_size=1 --eval.n_episodes=1 --eval.use_async_envs=false \
    --seed=42 --output_dir=outputs/arena-smolvla
```

The camera rename connects the native camera to this checkpoint's trained input. If a checkpoint already saves the desired rename processor, omit `--rename_map` to preserve it. An explicit `{}` clears saved renaming. Do not substitute cameras or change precision to hide an incompatible checkpoint.

### Evaluate PI0.5

Install the PI extra in the **policy environment**, retaining the other extras:

```bash
uv sync --locked --extra smolvla --extra pi --extra dataset --extra evaluation --extra remote
```

```bash
lerobot-eval \
    --policy.path=nvidia/pi05-arena-gr1-microwave \
    --policy.pretrained_revision=9cf88e758aeb86be15e0f44364cad19cede23188 \
    --policy.device=cuda \
    --env.type=envhub \
    --env.hub_path="$ARENA_ENVHUB" \
    --env.task=gr1_open_microwave \
    --env.server.endpoint=tcp/127.0.0.1:7448 \
    --rename_map='{"observation.images.robot_pov_cam_rgb":"observation.images.robot_pov_cam"}' \
    --eval.batch_size=1 --eval.n_episodes=1 --eval.use_async_envs=false \
    --seed=42 --output_dir=outputs/arena-pi05
```

<Tip>
  PI0.5 was validated with its saved bfloat16 and compilation settings.
  First-action compilation can take several minutes; the old instruction to
  disable compilation is no longer required for this tested stack. Its PaliGemma
  tokenizer assets must also be available with the appropriate access.
</Tip>

To evaluate two environments, set both `--eval.batch_size=2` and `--eval.n_episodes=2`, and choose a fresh output directory. Keep `--eval.use_async_envs=false`: the provider batches environments natively on the GPU.

### What to Expect

The evaluator reports episode progress, task success and aggregated metrics. The validated server runs completed three SmolVLA episodes across batches of one and two, and one PI0.5 episode, all successfully. The batched episodes finished at different steps. These small smoke runs establish inference and task completion for the pinned stack; they do not estimate general policy reliability or performance parity.

### Video Recording

The standard evaluator writes camera videos to the output directory. The provider enables the native camera in headless mode; the legacy `env.video`, `video_length` and `video_interval` flags are no longer used. Validated videos decoded at 512×512 and 50 fps.

Standard dataset recording is also available through `--robot.type=sim`, `--robot.env.type=envhub` and the environment server. See [simulation](./simulation) for the shared rollout options. For this mixed wrist-pose/hand-joint action space, set both `--return_to_initial_position=false` and `--strategy.reset_to_initial_position=false`.

A synchronous SmolVLA recording completed with uploads disabled: one finalized episode and 19 state/action/image frames. It achieved 3.71 Hz against a 50 Hz target, so it does not establish real-time operation. Current sim-robot omits the eight auxiliary state tensors available in evaluation; strict chunk/remote-policy paths requiring them are not qualified.

### Output Directory

With the explicit SmolVLA output directory above, evaluation results include:

```text
outputs/arena-smolvla/
├── eval_info.json
├── task_descriptions.json
└── videos/
    └── gr1_open_microwave_0/
        └── eval_episode_0.mp4
```

Use a new output directory for each evaluation.

## Environment Configuration

### Full Configuration Options

The provider declares the task schema through `LEROBOT_SIM`; dimensions and horizons are not CLI overrides.

| Setting                         | Value or option                                                                                     |
| :------------------------------ | :-------------------------------------------------------------------------------------------------- |
| Task                            | `gr1_open_microwave`; alias `gr1_microwave`                                                         |
| Controller                      | GR1 PINK                                                                                            |
| Primary state                   | 54 native joint positions, radians                                                                  |
| Actions                         | 36 values: left/right absolute wrist XYZ and `wxyz` quaternions, then 22 ordered hand joint targets |
| Camera                          | `robot_pov_cam_rgb`, 512×512 RGB                                                                    |
| Native control rate and horizon | 50 Hz; 5 seconds / 250 steps                                                                        |
| Simulator options               | `device`, `headless`, optional native `object` through `--sim.kwargs`                               |
| Evaluation batching             | `--eval.batch_size`, `--eval.n_episodes`, `--eval.use_async_envs=false`                             |

PINK actions are not joint-position commands. Each reset applies the supplied seed to its native slot; subsequent stochastic simulation shares the native RNG. Completed slots retain their first terminal observation and outcome at the provider interface while their peers finish, with zero subsequent reward and no replacement episode.

### Using Environment Hub directly for advanced usage

The provider exports lazy `vector_env_fns` for one native batch. Use the standard [EnvHub](./envhub) and [simulation](./simulation) interfaces for custom clients. Arena's registered Gym environment must be unwrapped for native `env_ids` resets; the provider handles that boundary.

### Migrating from the legacy Arena configuration

- Replace `--env.type=isaaclab_arena` with `--env.type=envhub` and the matching upgraded provider.
- Replace `--env.environment` with `--env.task=gr1_open_microwave`.
- Remove Arena-only `state_keys`, `camera_keys`, dimension, horizon and video options; use the declared native schema and standard evaluator recording.
- Remove the Arena-specific observation processor and `use_native_batch=true`. Native batching is selected through `vector_env_fns`.

## Creating New Environments

Create the native task and embodiment in [IsaacLab Arena](https://github.com/isaac-sim/IsaacLab-Arena), then follow [EnvHub](./envhub) to expose its vector factory and metadata. Define truthful state/action names, units, camera features, control rate and reset behavior. Test that schema before adding the task to the supported catalog; changing a dimension flag does not make another controller compatible.

<Tip>
  The native environment code and assets must be available in the simulator
  environment. The legacy `example_envs.yaml` mapping is not the new provider
  contract.
</Tip>

## Troubleshooting

### CUDA out of memory

Start with `--eval.batch_size=1`. The simulator and policy both consume GPU memory even when their Python environments are separate.

### EULA not accepted

Set these variables in the simulator environment before launch:

```bash
export OMNI_KIT_ACCEPT_EULA=YES ACCEPT_EULA=Y
```

### Video recording not working

Use the upgraded provider with its native camera enabled and inspect the evaluator's output directory. Do not restore the old Arena-specific video flags or substitute a different camera.

### Policy output dimension mismatch

Use a checkpoint trained for the native 54-state/36-action GR1 PINK contract. Check the camera rename and action ordering. Do not pad, clip or override dimensions to bypass a mismatch.

### In-process evaluation fails during import

Use the separate server. LeRobot eagerly imports G05 code requiring `get_vision_interpolation_indices_and_weights`, which Arena's pinned Transformers 5.10.4 does not provide. The tested client uses 5.22.1. No in-process GPU policy execution is qualified for this stack.

### Server startup is slow

First startup can compile shaders, cook collision geometry and load assets. Wait for `Serving`, inspect logs and use a bounded startup timeout. Check the server's actual exit status after stopping it. Native reset, malformed-action rejection, reconnect, normal shutdown and startup-error cleanup were exercised for the validated stack.
