# NVIDIA Isaac Lab-Arena

Isaac Lab-Arena runs through the standard [EnvHub](./envhub) native vector interface.
Use `lerobot-eval` for batched evaluation and `lerobot-env-server` to keep the simulator's
Python dependencies separate from the policy environment. The adapter owns the native
observations, actions and simulator lifetime; LeRobot needs no Arena-specific processor.

## Select a compatible stack

Use the upgraded Arena and EnvHub checkouts together. The old EnvHub repository that only
exports `make_env` does not implement this interface. Pin all three source revisions when
reproducing a run; see the EnvHub checkout's README for its installation recipe and tested
revisions. Do not combine the old Isaac Sim 5.1 / Isaac Lab 2.3 recipe with current Arena main.

The initial adapter supports **GR1 PINK opening the microwave**. It preserves the native
54-dimensional joint state, 36-dimensional absolute PINK command, 512×512 POV camera,
50 Hz control and five-second episode horizon (250 steps). PINK commands are not joint
position commands. Other embodiments and tasks require their own observation/action schema
and simulator metadata; changing a dimension flag cannot make a checkpoint compatible.

Install the simulator dependencies in the Arena environment/container and the policy extras
in a separate LeRobot environment:

```bash
# In the policy environment, from the matching LeRobot source checkout:
uv sync --locked --extra smolvla --extra dataset --extra evaluation --extra remote
source .venv/bin/activate
```

## Serve Arena and evaluate

After following the upgraded EnvHub README to install Arena and its matching native dependencies,
start the standard server **inside that simulator environment**. `ARENA_ENVHUB` is the absolute
path to the upgraded EnvHub checkout, visible inside the container if using Docker.

```bash
export OMNI_KIT_ACCEPT_EULA=YES ACCEPT_EULA=Y
export ARENA_ENVHUB=/absolute/path/to/isaaclab-arena-envs
lerobot-env-server \
  --envhub="$ARENA_ENVHUB" \
  --sim.task=gr1_open_microwave \
  --deployment=arena \
  --max_sessions=1 --max_envs=2
```

From the policy environment on the same host:

```bash
lerobot-eval \
  --env.type=envhub --env.hub_path="$ARENA_ENVHUB" \
  --env.server.endpoint=tcp/127.0.0.1:7448 \
  --env.server.deployment=arena \
  --policy.path=nvidia/smolvla-arena-gr1-microwave \
  --policy.pretrained_revision=1fab07da0ffb6c263c9703c296745a730a6ea696 \
  --policy.device=cuda \
  --rename_map='{"observation.images.robot_pov_cam_rgb":"observation.images.robot_pov_cam"}' \
  --eval.batch_size=2 --eval.n_episodes=2 --eval.use_async_envs=false \
  --seed=42 --output_dir=outputs/arena-smolvla
```

The explicit rename above connects the native camera to this checkpoint's trained camera name.
When a checkpoint already saves the desired rename processor, omit `--rename_map` to preserve it.
An explicit `{}` clears saved renaming. Missing cameras, incompatible state/action dimensions and
unavailable checkpoint assets must be fixed at their source; do not pad, substitute cameras or
change policy precision to hide a mismatch.

The server owns one simulator application and one native GPU batch. It can rebuild the world
when the requested batch changes, and supports one active client. It does not create a simulator
process per environment. Stop the server normally after clients disconnect, and check its actual
exit status as well as the evaluation results.

## Runtime qualification and recording

The Isaac Sim 6.2 server stack was exercised with SmolVLA in one- and two-environment batches
(three successful episodes), and PI0.5 in a one-environment batch (one successful episode).
Camera videos decoded at 512×512 and 50 fps. These small runs establish inference and task
completion for the pinned checkpoints, not a general success-rate or performance estimate.
Native reset regressions, malformed-action rejection, reconnect, normal shutdown and startup-error
cleanup were also checked. See the provider README for the source and dependency boundaries.

**Use the separate server for this stack.** In-process evaluation fails during CLI import:
LeRobot eagerly imports G05 code requiring `get_vision_interpolation_indices_and_weights`, which
Arena's pinned Transformers 5.10.4 does not provide. The tested policy client uses Transformers
5.22.1. Installing policy extras into the simulator would also conflict with its native package
versions; an in-process policy run is not qualified here.

LeRobot records evaluation video in the output directory. Its standard evaluation recording options
can also save rollouts as a dataset. The same descriptor is available through `--robot.type=sim`
with `--robot.env.type=envhub` and the server endpoint for standard rollout/recording workflows.
One standard synchronous SmolVLA episodic recording completed with uploads disabled. It recorded
primary state, action and camera data; the eight auxiliary state tensors available in evaluation
are not forwarded by the current sim-robot interface. Strict chunk/remote-policy validation that
requires those tensors is therefore not qualified. The smoke recording achieved 3.71 Hz against
a 50 Hz target, so it is not evidence of real-time operation. Disable both rollout and episodic
return-to-initial-position options for this mixed wrist-pose/hand-joint command space.
This is not a teleoperation controller for GR1 PINK.
See [simulation](./simulation) for the shared CLI options.

## Migration from the legacy Arena path

- Replace `--env.type=isaaclab_arena` with `envhub` and a matching upgraded provider.
- Remove `state_keys`, `camera_keys`, `state_dim`, `action_dim`, `episode_length`, and the Arena-specific
  video options. The provider defines the native schema and horizon; the evaluator owns recording.
- Do not use `use_native_batch=true`: that legacy bypass skips the shared simulator interface.
  The provider's `vector_env_fns` selects native batching automatically.
- Remove the Arena observation processor and bespoke evaluation/process wrappers. Canonical
  conversion, policy loading and processor pipelines use the standard LeRobot paths.

Each reset applies its supplied seed to the corresponding native slot. Subsequent stochastic
simulation still shares the native RNG; this is not a guarantee of independent random streams.
Completed slots return their first terminal observation and outcome until explicit reset while other
slots finish. No replacement episode contributes to the result.

A successful installation or contract test is distinct from learned inference and task success.
Only the exact checkpoint/controller/task/runtime combinations exercised by a runtime report are
qualified. Old PI0.5 and SmolVLA results from previous integration revisions are not results for this migration.
