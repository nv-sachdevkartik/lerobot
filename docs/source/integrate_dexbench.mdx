# RLWRLD DexBench

Select DexBench with `lerobot-eval --env.type=dexbench` after installing the optional `lerobot_env_dexbench` plugin in the prepared DexBench simulator runtime. DexBench owns native tasks, observations/actions, replay and simulator startup/closure. LeRobot supplies policy factories, processors and the evaluation loop. EnvHub can distribute the environment entry point.

## Prepare the runtime

Use the DexBench repository's documented Isaac Sim/Arena runtime and assets. The integration requires the LeRobot candidate that includes the generic `EnvConfig.get_evaluation_runner()` hook; the earlier v1 correctness fixes alone are insufficient. Install all three components in that same Python environment:

```bash
python -m pip install --no-deps -e /path/to/lerobot-dexbench-integration
python -m pip install --no-deps -e /path/to/DexBench-lerobot-integration/source/dexbench_arena
python -m pip install --no-deps /path/to/DexBench-lerobot-integration/integrations/lerobot/plugin
lerobot-eval --help
```

`--no-deps` preserves the already provisioned simulator stack; these commands do not install Isaac Sim, assets or policy dependencies. The tested simulator environment has dependency deviations, including NumPy 2.3.5 above LeRobot's declared upper bound, so this is not a clean dependency-resolution recipe.

## Select a task

Use the complete ACT example in the DexBench checkout's `integrations/lerobot/README.md` as a first interface check. Its environment selection is:

```json
{
  "env": {
    "type": "dexbench",
    "environment": "dexbench_logistics_center_e2_environment",
    "base_adapter": "/absolute/path/to/pinned-arena-adapter",
    "device": "cpu",
    "dexbench": { "task": "lift_to_conveyor", "anchor": "A1_CAGE" },
    "evaluation": { "action_mode": "step", "policy_image_size": [180, 320] }
  }
}
```

This fragment also needs a policy, evaluation budget and new output directory. `base_adapter` contains the qualified Arena `env.py` and `isaaclab_env_wrapper.py`, or is a full-commit-pinned Hub adapter with explicit remote-code consent. `env.dexbench.task` selects the native task; `env.task` is the language instruction.

```bash
lerobot-eval --env.type=dexbench --config_path=/absolute/path/to/act-l2.json
```

If the container requires Isaac Sim's interpreter wrapper:

```bash
/isaac-sim/python.sh /isaac-sim/kit/python/bin/lerobot-eval \
  --env.type=dexbench --config_path=/absolute/path/to/act-l2.json
```

Both invoke the standard installed LeRobot entry point. Plugin discovery registers `dexbench` before parsing and starts no simulator for help or unrelated environments. The selected runtime starts Isaac Sim before task construction and closes owned environments/application on return or failure.

The DexBench runner owns a command process. It uses Isaac Sim's documented shutdown API with `exit_code`, waits for recorder work, and preserves evaluation failures. Native shutdown may terminate the interpreter, so invoke the command as a separate process rather than inside a notebook or long-lived service. The prepared runtime must provide `SimulationApp.close(exit_code=...)` (available in the documented Isaac Sim 6 API). Full extension-by-extension teardown is not qualified in the tested runtime.

## Processing and replay

Provider controls live under `env.evaluation`: action mode, execution steps, processor path/overrides, image size, whole-policy dtype casting, rendered episode limit, policy variant and policy metadata. The legacy DexBench launcher retains its top-level fields; do not combine the two formats.

For a qualified GR00T replay recipe, retain the trained checkpoint and processor configuration, BF16 model/FP32 decoded actions, 180×320 stereo input, 40 predicted actions and 16 executed actions. Use `env.evaluation.action_mode=chunk`, `execution_steps=16`, and the verified absolute-action metadata. These settings do not make an unrelated checkpoint compatible.

Set `env.recorded_variation_samples_path` to admitted frozen rows with their exact sidecar, and `eval.n_episodes` to that row count. The adapter handles native autoreset without skipping rows or reseeding subsequent episodes. Native results are saved in `native_episodes.jsonl` alongside `run_config.json`, `runtime_contract.json` and `eval_info.json`.

Only one synchronous environment is currently qualified. Native task limits and success criteria are preserved. Optional `env.simulator_cache_dir` provides a separate absolute compiled-cache location; it is not a generic Kit argument interface.

## Qualification limits

A successful standard-command run proves the integration path, not task-performance parity. V1 retains one unresolved 30-row M1 run and measured H1/L2 deficits. Existing inference evidence covers 10 policy families with 16 documented constraints; those are not all trained task-success results. The new command requires its own source-bound simulator validation. Remote policy serving remains separate future work.
